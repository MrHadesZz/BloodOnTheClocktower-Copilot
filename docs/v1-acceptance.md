## 修复的行为

1. 图书管理员的健康零外来者报告原先直接要求真实外来者数量为零，会错误排除健康隐士注册为爪牙或恶魔的世界。现在按本次注册判断，并在见证中记录 `librarian_zero_<index>`；具体重放拒绝遗漏或中毒时使用的注册。界面显示中文注册解释。
2. 小恶魔自杀时枚举健康隐士的爪牙注册候选，并通过独立的 `alignments` 保留实际善良阵营。角色变化不会重新计算阵营：后续共情者读取实际阵营，占卜师读取恶魔角色，胜负检查存活恶魔及存活人数。隐士接任见证包含唯一的本次爪牙注册和末阶段实际阵营。健康红唇女郎仍优先，中毒或已死的隐士不能作为本次候选。
3. 手机样式原先隐藏了魔典顶部高级推理按钮。现在保留图标入口和可访问名称；手机可以进入高级工作区、导入记录并查看规则见证。
4. 标准 7–15 人路径允许首夜和后续夜晚的单投毒者自选；投毒效果保持到黄昏，来源死亡或失去投毒者角色则提前结束。自毒不会阻止健康小恶魔的传位让其取得新角色。What-if、schemaVersion 2 工作区导入和恢复均已接入；固定八人 H0 教学分支的旧枚举假设本轮未扩展。
5. 显式行动与观察历史的查询见证都携带角色和实际阵营。后续共情者、占卜师重放读取提供的注册选择，逐个检查目标，允许合法替代组合，并拒绝缺项或篡改。
6. 健康隐士实际死亡时，可以在红唇女郎自己的判定中注册为小恶魔。该选择与猎手注册独立；死亡前五人阈值和双方健康状态在这次判定中检查。原小恶魔继续存活，见证显示存活恶魔名单。多个恶魔的日夜重放不因杀死其中一位就直接判善良胜利。
7. 夜晚开始时多个小恶魔分别提供完整队列，每次攻击即时更新死亡、角色、毒效、保护和胜负，新继任者本夜不再行动。来源死亡或变身会影响后续攻击。遗漏、重复、错误行动者、篡改目标、伪造跳过和额外爪牙注册同时经 TypeScript 与 Python 审计。界面允许镇长转移等不同合法见证，不将某一组隐藏选择固定成事实。
8. 守鸦人死亡时立即固定角色、毒效与注册资格，避免看见后来才取得的小恶魔角色、夜末恢复后补发信息或允许较早的中毒目标特殊注册。已获得的信息在后续终局前保留。观察搜索、条件细查、界面说明和独立 Python 校验使用相同时点，独立核对具体信息目标，拒绝篡改目标、缺少选择和反转行动顺序。机制和 22 角色审计边界见 [信息时点说明](./design/information-timing.md)。

9. 计票的人数门槛在本次计票时固定，后来的击杀不会使较早失败的投票生效。猎手造成善良或邪恶终局后，不再结算票数领先者，避免再次处决改变胜负。白天处决与其造成的死亡分别记录，猎手死亡后被处决的尸体不会产生送葬者信息。原始记录的提名至计票之间插入公开行动时，明确提示未支持并保留顺序。依据、独立实现和范围见 [白天事件顺序](./design/day-order.md)。

10. 记录面板提供按原位置纠正投票，保留被撤回的原文和旧举手名单；反复纠正不移动发生位置，撤回替代记录不会复活旧投票，修改后必须重新确认本日完整。旧分支仍查询原记录，追加和撤回需先显式更新。公开导出不泄露私密纠正，受损引用在导入前拒绝。操作和格式见 [投票纠正说明](./design/vote-corrections.md)。

当前规则版本：首夜 `tb-standard-setup-first-night-v4`，显式时间线 `tb-standard-bounded-timeline-v7`，观察时间线 `tb-standard-observed-timeline-v8`；独立 oracle `tb-finite-python-v6`。旧 schemaVersion 2 工作区继续读取；第一次使用投票纠正时保存为 3，以确保旧程序不会忽略纠正关系。含公开纠正的公开导出为 schemaVersion 2，私密纠正不改变公开导出格式。答案仍由事件重新生成。

图书管理员零信息和隐士继任的处理是依据各能力及通用注册、阵营规则作出的组合推导，官方角色页没有直接列出本项目的测试输入。依据：[图书管理员](https://wiki.bloodontheclocktower.com/Librarian)、[隐士](https://wiki.bloodontheclocktower.com/Recluse)、[小恶魔](https://wiki.bloodontheclocktower.com/Imp)、[角色与阵营、醉毒状态](https://wiki.bloodontheclocktower.com/States)。厨师逐边注册参考[厨师官方示例](https://wiki.bloodontheclocktower.com/Chef)，持续效果参考[投毒者](https://wiki.bloodontheclocktower.com/Poisoner)，其余切片参考[红唇女郎](https://wiki.bloodontheclocktower.com/Scarlet_Woman)、[镇长](https://wiki.bloodontheclocktower.com/Mayor)、[僧侣](https://wiki.bloodontheclocktower.com/Monk)及[间谍](https://wiki.bloodontheclocktower.com/Spy)。

**自毒是有边界的模型推导。** 投毒者官方页允许选择任意玩家，明确当夜至次日和黄昏恢复，并举例来源变成小恶魔时效果结束；没有直接解释投毒者自毒的循环。[寡妇官方页的自毒示例](https://wiki.bloodontheclocktower.com/Widow)支持“能力失效而自毒不反复开关”的处理。本项目据此在单毒源 TB 中采用自选后持续的模型，不将它声称为官方给出的通用醉毒循环裁定，也未实现寡妇。状态传播、证据约束和范围见 [机制说明](./design/alignment-and-self-poison.md)。

**隐士死亡触发红唇女郎与多恶魔队列是规则组合推导。** 依据隐士死亡后可逐次注册、红唇女郎继任能力和[多个恶魔的通常胜利条件](https://wiki.bloodontheclocktower.com/Pit-Hag)组合实现，不声称官方页列出了本项目的完整测试场景。夜晚开始时的恶魔各行动一次，新继任者当夜不追加攻击；持续效果的即时终止依据[能力规则](https://wiki.bloodontheclocktower.com/Abilities)。具体推导、信息步骤、字段与预算边界见 [多恶魔夜晚说明](./design/multi-imp-nights.md)。

## 历史性能基线（本轮暂缓）

以下数据来自 2026-10-01 的阵营、自毒增量，规则版本为首夜 v4、显式时间线 v3、观察时间线 v4。本轮没有重跑基准或进行 Worker 性能优化，不将历史数字作为当前规则版本的实测结果。

合成样例为 10/12/15 人 × 稀疏/中等/密集信息 × N2/N3，共 18 个工作负载。所有样例都封闭日夜阶段，包含 D1 提名投票、处决死亡和后续夜死。稀疏样例不固定身份、不采纳报告；中等与密集样例固定相同的前六位身份，其他身份保持隐藏。15 人增加明确的首夜投毒假设。中等采纳各夜共情者报告；密集增加占卜师、首夜厨师/洗衣妇和 N2 送葬者报告，N2 共 7 份、N3 共 9 份。

所有返回见证同时经过 TypeScript 与独立 Python 审计。另以 100ms、单设置候选和单历史候选测试预算边界：Node 3 项、浏览器 6 项均返回未知，并保留时间或候选预算原因；未知没有被转换为“不可能”。

P95 采用最近秩法。每格仅 3 或 5 个样本时，P95 即样本最大值，不是稳定的分位数估计。手机仅改变视口，没有模拟手机 CPU 或真实硬件。原始 JSON 保存每次耗时、结论、未知原因和边界结果。测量的是单个身份查询，不是“一键分析”或多人组合总耗时，也不包含记录提交的 IndexedDB/界面延迟。

桌面冷 Worker 样本尚未达到 TDD 的约 300ms 常用查询目标。复杂查询 2 秒预算在本次样例中足够，仍不能据此放行完整性能门槛；记录提交 P95 50ms、实际手机、更多历史和完整未知率验收尚待完成。

## 复现命令

运行需要 Node.js 22.12+ 和 Python 3，命令在项目目录执行。

```bash
npm test
npm run test:rules
npm run build
# 在一个终端启动生产预览，另一个终端运行浏览器检查：
npm run preview -- --host 127.0.0.1 --port 4176 --strictPort
PLAYWRIGHT_BASE_URL=http://127.0.0.1:4176 PLAYWRIGHT_OFFLINE=1 npm run test:e2e
# 后续恢复性能工作时再运行：
BENCH_OUTPUT=output/v1-performance-node.json npm run bench:v1
PLAYWRIGHT_BASE_URL=http://127.0.0.1:4176 BENCH_OUTPUT=output/v1-performance-browser.json npm run bench:v1:browser
```

如使用已有 Chromium，设置 `PLAYWRIGHT_EXECUTABLE_PATH`。`BENCH_REPETITIONS` 可增加样本次数；`BENCH_BUDGET_MS` 默认 2000。Node 与浏览器分别运行，避免测试竞争 CPU。基准生成文件放在已忽略的 `output/`。本轮投票纠正截图与旧格式、纠正后的可导入记录另保存为当前 Codex 对话的交付文件；性能测量仅保留历史数据。
