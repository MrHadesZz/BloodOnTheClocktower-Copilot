# 白天事件顺序、计票时点与处决死亡来源

更新：2026-10-03。适用于标准 7–15 人 Trouble Brewing 的有限历史模型；本轮独立矩阵扩展 9/12/15 人切片，性能工作继续暂缓。

## 实际修复

先写出的七项回归在旧实现中复现四项失败：较早未达到人数门槛的投票在后来死亡后被错误通过；猎手造成终局后仍追加待处决，可能让圣徒翻转善良胜利或让最后恶魔被错误处决；猎手死亡与随后尸体处决被误算为处决死亡，产生不应存在的送葬者信息。

现在分别固定每次计票时的人数门槛、即时终局、执行的处决及真正由处决造成的死亡。已经发生的投票和遗言票保留，后来的死亡或贞洁者触发不会撤回这些公开历史。

| 已验证的场景 | 当前结果 |
| --- | --- |
| 9 人存活时某人获 4 票，随后猎手击杀隐士 | 该次投票仍未达到 5 票门槛，不处决原候选 |
| 先猎手击杀隐士，再在 8 人存活时取得 4 票 | 使用本次 4 票门槛，可按最高票规则处决 |
| 较早未通过的 4 票，死亡后另一人也获 4 票 | 最高票仍为平票，不处决其中任何人 |
| 圣徒已经票数领先，随后猎手击杀最后恶魔 | 善良立即胜利，不再处决圣徒 |
| 3 人存活时隐士被猎手击杀，恶魔仍活 | 邪恶立即胜利，不再结算较早的待处决恶魔 |
| 猎手先击杀某人，之后票决其尸体 | 有处决，无处决死亡；下一夜送葬者不因此获得信息 |
| 猎手击杀一人，之后另一个活人被处决 | 后者是处决死亡来源，送葬者可获得对应信息 |
| 圣徒已经票数领先，随后镇民提名健康贞洁者 | 提名者立即被处决，覆盖待处决；此前遗言票仍已消耗 |

## 规则依据与推导范围

[官方词汇表](https://wiki.bloodontheclocktower.com/Glossary)规定处决的人数门槛、票数必须超过其他候选、遗言票和胜负条件；[猎手](https://wiki.bloodontheclocktower.com/Slayer)的有效击杀即时发生；[贞洁者](https://wiki.bloodontheclocktower.com/Virgin)触发后立即处决提名者并结束当天。[状态规则](https://wiki.bloodontheclocktower.com/States)区分处决与死亡，死者可以被处决但不能再次死亡；[送葬者](https://wiki.bloodontheclocktower.com/Undertaker)要求死亡由处决造成。

计票时人数与其后能力击杀的组合输入，是按这些规则的时序作出的有限模型推导，官方页没有逐一列出本项目的测试场景。最高票比较保留全部较早计票，平票不能通过重新计算人数来打破。

每个 `DayEvent.nomination` 目前将提名及其完整计票作为一个步骤。原始记录若在提名与关联计票之间插入猎手、另一提名、处决、死亡或胜负，录入层返回未支持并明确提示，保留实际顺序；不将其静默合并为已支持历史。普通声称不改变这个公开行动顺序。这仍不是任意投票中断或旅人规则的实现。

## 状态、界面与独立审计

`DayTrace.nominationTallies` 增加 `eventIndex`、`aliveAtVote` 与 `threshold`，使用本次计票时的人数。`eventSteps` 逐项保存死亡、即时处决、行动后的存活人数及胜负；`endedAfterEventIndex` 记录即时结束的位置。`executedSeat` 与 `executionDeathSeat` 分别表示执行的处决及其造成的死亡，`executionCause` 区分票决和贞洁者触发。

显式重放、观察搜索和独立 Python 校验均从 `executionDeathSeat` 派生下一夜送葬者的死亡来源。界面从行动见证重新重放这些字段，按顺序显示计票人数、所需票数、猎手结果、即时结束和尸体处决说明；这些字段不保存为工作区的隐藏真相。

Python 独立模型使用逐次维护待处决的方式；应用使用本次计票门槛及完整最高票比较。新增有限输入验证不同人数、行动顺序、平票、首次使用、醉毒、注册、死者票和终局，观察历史包含有效信息与不可能的信息反例。具体见证反转公开行动后，同时由 TypeScript 和 Python 拒绝。
